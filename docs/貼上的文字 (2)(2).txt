## 核心建議

這個問題不宜預先設成「供給不足」與「調度／碎片化」的二選一。**GPU type isolation 本身就會限制 A10 作業能使用的供給；調度則決定有限供給先服務誰。**兩者可能同時重要，而且對平均等待與尾部等待的重要性不同。

建議採用兩層框架：

> **第一層：用受控反事實，分解增容、兼容性開放與既有調度改進的收益。**  
> **第二層：用節點級可行性診斷和約束消融，解釋 CPU/GPU mismatch、空間碎片與 gang 同步限制如何影響這些收益。**

M0–M4 可以保留，但**不能直接當成五個依序改善的階段**：M2 是完全放寬兼容性的理想化情景，M3 是有限替代，後者不是在前者之上「再加一項改善」。

### 已有證據對框架的約束

現有資料已經讓部分假說比其他假說更值得優先檢驗。

# 一、數學定義

## 1.1 研究對象：固定原始作業群，而不是固定執行位置

令作業 \(j\) 的原始屬性為

\[
(a_j,p_j,w_j,q_j,c_j,g_j^0),
\]

依次代表到達時間、原始時長、worker 數、每 worker GPU／CPU 需求、原始請求型號。

節點 \(m\) 的屬性為

\[
(G_m,C_m,g_m).
\]

定義固定的 A10 研究群：

\[
\mathcal J_A=\{j:g_j^0=\mathrm{A10}\},\qquad N_A=111284.
\]

**A10 作業轉到 A100 執行後，仍然屬於 \(\mathcal J_A\)。**否則，將轉出的作業從 A10 等待統計移除，就會產生選擇偏差。

用

\[
z=(\mathcal C,K,\kappa,\pi;R_0,P_0)
\]

表示一個反事實世界，其中：

| 符號 | 意義 |
|---|---|
| \(\mathcal C\) | 實際物理節點及 CPU/GPU 容量 |
| \(K_{jg}\in\{0,1\}\) | 作業 \(j\) 是否允許在型號 \(g\) 執行 |
| \(\kappa_{jg}>0\) | 在型號 \(g\) 執行的時長倍率 |
| \(\pi\) | 已有、凍結的調度策略 |
| \(R_0\) | 凍結的跨型號路由／分流規則 |
| \(P_0\) | 凍結的節點放置規則 |

主實驗保留 worker 數與資源需求，且同一作業使用同一種實際 GPU 型號 \(h_j\)：

\[
K_{j,h_j}=1,\qquad
f_j=s_j+\kappa_{j,h_j}p_j.
\]

所有 workers 同步開始、配置固定、不可搶占，每個 worker 的 CPU/GPU 仍由同一節點提供。這些是沿用原題與 Q2 的基本契約；兼容性是 Q3 明確改動的部分。Q2_正式實驗協議

這裡估計的是**固定 trace、固定模型假設下的干預效果**，不是從資料識別出歷史真實排隊原因。原始 CSV 沒有歷史開始時間，也沒有跨型號實測效能。閱讀資源摘要

## 1.2 主結果與保護結果

主要反應變數使用：

\[
Y_A(z)
=
\overline W_A(z)
=
\frac{1}{N_A}
\sum_{j\in\mathcal J_A}[s_j(z)-a_j].
\]

並同時計算 A10 的 P95、P99、Max waiting、長作業分層等待，以及原始各型號作業的結果。

對任意兩個世界：

\[
\Delta_A(z_0,z_1)=Y_A(z_0)-Y_A(z_1),
\]

正值表示改善。相對降幅為

\[
r_A(z_0,z_1)
=
\frac{\Delta_A(z_0,z_1)}{Y_A(z_0)}.
\]

基準值為零時，只報絕對差，不計相對百分比。

此外，

\[
JCT_j(z)=W_j(z)+\kappa_{j,h_j}p_j.
\]

因此，跨 GPU 替代後：

\[
JCT_j(z_0)-JCT_j(z_1)
=
\underbrace{W_j(z_0)-W_j(z_1)}_{\text{等待節省}}
+
\underbrace{p_j(z_0)-p_j(z_1)}_{\text{執行時間變化}}.
\]

**減少等待但大幅延長執行時間，不一定改善完成時間。**

異構 GPU 對不同工作負載的性能差異，也是 Gavel 研究強調必須顯式建模的部分；不能僅依 GPU 名稱推定倍率。[USENIX](https://www.usenix.org/conference/osdi20/presentation/narayanan-deepak)

## 1.3 M0–M4 的明確定義

三項收益分解的主實驗，先統一採用：

\[
\boxed{\kappa_{jg}=1}
\]

這是為了隔離資源可達性效果而設定的情景假設，**不是聲稱不同 GPU 真實性能相同**。

| 情景 | 物理容量 | 兼容性 | 調度 | 回答的問題 |
|---|---|---|---|---|
| **M0：原始隔離** | 原始 \(\mathcal C_0\) | 僅原型號 \(K_0\) | \(\pi_0\) | 原始基準 |
| **M1：增加 A10 capacity** | \(\mathcal C_\delta\) | \(K_0\) | \(\pi_0\) | 不改兼容性與策略，增容能改善多少？ |
| **M2：解除 type isolation** | \(\mathcal C_0\) | 理想全兼容 \(K_{\rm all}\) | \(\pi_0\) | 不增硬體，完全放寬型號限制能改善多少？ |
| **M3：有限 substitution** | \(\mathcal C_0\) | 有限兼容 \(K_{\rm lim}\) | \(\pi_0\) | 在受限兼容範圍內能取得多少收益？ |
| **M4：加入 scheduling improvement** | \(\mathcal C_0\) | 與 M3 相同 | \(\pi_1\) | 固定替代情景後，既有 Q2 策略再改善多少？ |

其中：

**M1 增加完整 A10 節點。**按事前固定的 CPU 類別、取整與新增 ID 規則增加節點；不把單 GPU 節點直接改成多 GPU 節點，否則同時改變了節點形狀。這個效果應稱為「A10 節點容量效果」，包含新增節點配套的 CPU。

**M2 保留節點級 CPU/GPU、worker 不可分割及 gang 限制。**不能把「解除型號限制」同時做成「所有 CPU/GPU 都能跨節點任意拼接」。

**M3 的有限性至少包括兩項：**哪些 A10 作業可替代，以及它們能去哪些目的型號。其他型號的原生作業仍全部保留。

**M4 僅更換已存在的策略。**立即可用的排序參照是 FCFS-HOL 與 SJF-HOL，採同一 First-Fit；之後可用 Q2 正式凍結、通過驗證的版本替換 \(\pi_1\)，不在 Q3 再設計新調度器。既有 Q2 文件已明確區分策略規格與尚未完成的性能驗證。Q2_正式實驗協議 Q2_Gang_Scheduling_研究設計與Codex規格

**M2 是理想化參照，不自動是等待下界。**放寬可行域只能保證相應最優值不變差；固定啟發式與固定路由的實測結果，不必單調改善。

## 1.4 如何得到 capacity＋compatibility＋scheduling 分解？

只跑五個命名情景，通常不夠。

選定一個增容量 \(\delta\) 和一個有限兼容方案，建立三個二元因素：

\[
C\in\{0,1\},\quad B\in\{0,1\},\quad S\in\{0,1\},
\]

分別表示是否增容、是否開放有限兼容性、是否使用 \(\pi_1\)。記

\[
Y_{cbs}=\overline W_A(C=c,B=b,S=s).
\]

需要完整的 \(2^3=8\) 個組合。

### 方法 A：有順序的增量分解

例如按「增容 → 兼容性 → 調度」：

\[
\Delta_C^{\rm path}=Y_{000}-Y_{100},
\]

\[
\Delta_B^{\rm path}=Y_{100}-Y_{110},
\]

\[
\Delta_S^{\rm path}=Y_{110}-Y_{111}.
\]

則必有

\[
\boxed{
Y_{000}-Y_{111}
=
\Delta_C^{\rm path}
+
\Delta_B^{\rm path}
+
\Delta_S^{\rm path}
}
\]

但這些是**指定順序下的邊際收益**。先開放兼容性，可能已消除部分容量壓力，之後增容的邊際收益就會變小。

尤其不能把

\[
(Y_{000}-Y_{100})
+
(Y_{000}-Y_{010})
+
(Y_{000}-Y_{001})
\]

直接稱為總改善，因為它可能重複計算相同作業的等待節省。

### 方法 B：Shapley 順序平均分解——推薦作正文主結果

令因素集合 \(F=\{C,B,S\}\)，\(Y(T)\) 表示只啟用子集 \(T\) 中因素的等待。對因素 \(i\)：

\[
\phi_i
=
\sum_{T\subseteq F\setminus\{i\}}
\frac{|T|!(2-|T|)!}{3!}
\left[Y(T)-Y(T\cup\{i\})\right].
\]

這相當於對六種干預順序的邊際貢獻取平均，採用 Shapley 分配思想。[劍橋大學出版社](https://www.cambridge.org/core/books/abs/shapley-value/value-for-nperson-games/1AA9D343DE7A87A97F69E999D329B57A)

由每條順序上的差值相消，可得：

\[
\boxed{
\text{Waiting reduction}
=
\phi_C+\phi_B+\phi_S
=
Y_{000}-Y_{111}
}
\]

其正確解釋是：

> 在指定增容量、兼容集合、路由規則及兩個固定策略下，把聯合改善分配給三項干預。

它**不是與情景設定無關的自然原因占比**。應同時展示條件邊際效果或交互效應，例如：

\[
I_{CB}
=
(Y_{000}-Y_{110})
-(Y_{000}-Y_{100})
-(Y_{000}-Y_{010}).
\]

負的 \(I_{CB}\) 表示兩項干預有部分重複收益；正值表示互補。負的 Shapley 貢獻也應保留，不得截成零。

還有一個重要界限：**M4 本身沒有增容。**因此，M0→M4 的改善應分解為兼容性與調度；上面的三項分解對應的是「M4 再加上所選增容量」的聯合終點 \(Y_{111}\)。

# 二、實驗設計

## 2.1 最小主實驗：12 個配置

推薦主矩陣：

\[
\boxed{
2\text{ 種容量}
\times
3\text{ 種兼容設定}
\times
2\text{ 種既有策略}
=12
}
\]

| 因素 | 主設定 |
|---|---|
| 容量 | 原始；A10 節點約增加 25%，報告取整後實際增幅 |
| 兼容性 | 原始隔離；有限兼容；理想全兼容 |
| 策略 | \(\pi_0\)；\(\pi_1\) |
| 時長倍率 | 全部為 1 |
| 放置 | 相同、凍結的 \(P_0\) |
| 到達／作業集合 | 全部 224,112 個作業保持不變 |

其中「隔離／有限兼容」的八格用於三因素分解；另外四格用於理想全兼容參照。

有限兼容的第一個固定設定，可以採用：**預先選定比例的 A10 作業，允許使用 A100 或 A800**。比例只是研究情景，不能宣稱是資料識別出的真實兼容率。

## 2.2 固定分流，避免偷偷加入另一套 scheduler

**開放兼容性不會自動決定作業去哪裡。**因此 \(R_0\) 必須寫入實驗契約，否則 compatibility effect 會混入未說明的路由改進。

為直接復用既有 Q2，主實驗可採用「提交時一次性固定分流」：

作業到達時，根據允許型號集合、靜態節點配置，以及事前凍結的作業 ID 雜湊與目的池權重，決定實際池；目的池必須滿足該作業的空池可行性。之後不重新選池、不遷移，各池使用原有 Q2 scheduler。

目的池權重使用原始容量設定並凍結，不能在增容格或更換 scheduler 時重新調整。相同兼容設定在 \(\pi_0,\pi_1\) 下，必須得到相同路由表。

這個設計的優點是：物理池仍然互不重疊，既有單池預約邏輯可以直接復用；但其結論必須寫成：

> **兼容性開放在固定分流規則下的效果。**

不能寫成所有動態共享方案的最大收益。

若後續研究真正的共享等待隊列，同一作業可以競爭多個池，則必須重新核驗跨池預約：**不同池各自有一份可行證書，不代表它們能同時使用重疊節點。**Q2 的單預約安全推導不能直接繼承到這種情況。Q2_Gang_Scheduling_研究設計與Codex規格

## 2.3 全部原生作業共同重播，不能創造「免費接收池」

每個目的池的工作負載必須包括：

\[
\text{該池原生作業}
+
\text{全部被分流至該池的作業}.
\]

每個物理節點只能出現在一份資源帳本中。不能一邊將 A100 節點提供給 A10，另一邊又讓原生 A100 作業使用未扣除的同一容量。

這正是既有 Q3 審查指出的證據缺口：只有額外節點持續可用的 overflow 模型，不能證明動態借用既有資源且不傷害原生作業。生成深度研究提示詞

原生作業保護至少報告：

\[
H_g^+
=
\sum_{j:g_j^0=g}
\max\{0,W_j(z)-W_j(M0)\},
\]

以及新增等待作業數、P99 額外等待、最大額外等待。對原本零等待的池，應使用秒數和作業數，而不是被四捨五入成零的平均小時數。生成深度研究提示詞

全叢集淨改善也要核算：

\[
N\Delta\overline W_{\rm all}
=
N_A\Delta\overline W_A
+
\sum_{g\ne A10}N_g\Delta\overline W_g.
\]

**A10 改善但其他池損失更大，不能稱為叢集改善。**

## 2.4 共用時間、事件與驗證契約

正式主表採用 Q2 的固定窗口：

\[
H=90\times86400=7,776,000\text{ 秒}.
\]

所有作業從 \(t=0\) 空叢集開始重播，最後一次到達後繼續排空；等待與 JCT 對全部原始作業評分，完成數和分配率在 \([0,H]\) 評分。Q1 原窗口 7,775,878 秒可另行重算，但不能混用。Q2_正式實驗協議

所有配置沿用同一套完成／到達處理、排序平手、放置、timer 和每 timestamp 掃描預算契約。**相同的是事件規則，不是強迫不同世界具有相同完成事件時刻。**

獨立驗證至少包括逐節點容量、每作業完整 workers、非搶占、實際時長、路由合法性及全部完成。另核對：

\[
\int Q_A(t)\,dt
=
\sum_{j\in\mathcal J_A}W_j,
\]

其中 \(Q_A\) 依原始 A10 身份統計，包括已轉往其他池但尚未開始的作業。

當 \(\kappa=1\) 時，完整排空後的 GPU 分配時間總量在各策略間相同；當 \(\kappa\ne1\) 時，應核對實際的 \(\sum_jw_jq_j\kappa_{j,h_j}p_j\)，不能再要求原始 GPU-hours 不變。

## 2.5 如何分辨 fragmentation、gang 與 CPU/GPU mismatch？

三因素分解回答「哪種干預有效」，尚不能單獨回答「哪種物理限制造成了等待」。後者需要節點級診斷。

在每個完成調度後的狀態，令節點剩餘資源為 \(F_m^G(t),F_m^C(t)\)。作業 \(j\) 在節點上的可放 worker 數：

\[
h_{jm}(t)
=
\begin{cases}
\min\!\left(
\left\lfloor F_m^G(t)/q_j\right\rfloor,
\left\lfloor F_m^C(t)/c_j\right\rfloor
\right),&c_j>0,\\[4pt]
\left\lfloor F_m^G(t)/q_j\right\rfloor,&c_j=0.
\end{cases}
\]

對型號 \(g\)：

\[
H_{jg}(t)=\sum_{m:g_m=g}h_{jm}(t).
\]

同一作業不混用 GPU 型號時，立即可放置當且僅當：

\[
\max_{g:K_{jg}=1}H_{jg}(t)\ge w_j.
\]

這延伸了 Q2 已有的相同 workers 精確槽數判定。Q2_Algorithm_Audit

據此記錄：

| 診斷 | 狀態判準 | 解釋限制 |
|---|---|---|
| 原池資源不足 | 原池可用 GPU 或 CPU 總量不足 | 是當下狀態，不代表不受先前排序影響 |
| 型號隔離暴露 | 原池不能完整放置，但某替代池可以 | 表示當下有替代機會，不保證替代後無外部代價 |
| GPU 空間碎片 | GPU 總量足夠，但 \(\sum_m\lfloor F_m^G/q_j\rfloor<w_j\) | 排除 CPU 後的純 GPU 裝箱限制 |
| CPU／同節點配比限制 | GPU slots 足夠，但完整 CPU/GPU slots 不足 | 再區分 CPU 總量不足與 CPU/GPU 分散於不同節點 |
| gang 同步暴露 | \(0<H_{jg}<w_j\) | 部分 workers 可放、整個 job 不可放；不是獨立因果占比 |
| 策略／預約／掃描限制 | 物理可完整放置卻仍未啟動 | 必須從派送與預約日誌區分原因 |

這裡有一個**可以直接推導的 A10 特性**：

因 \(q_j=1\)，GPU 剩餘量為整數，

\[
\sum_m\left\lfloor F_m^G/1\right\rfloor
=
\sum_mF_m^G.
\]

因此，在沒有其他拓撲限制的模型下，**A10 的純 GPU 整數裝箱碎片判準不會成立**。這不排除 CPU 同節點限制、型號隔離或等待同步資源的時間損失。

A10 的 CPU 限制也接近冗餘：只有兩個節點為 126 vCPU，其餘為 128；CPU 請求超過 126 的 A10 作業只有 13 個，且都是單 worker。這支持優先檢查容量與排序，但不能用少數作業占比直接限制其可能造成的 HOL 傳播影響。Q2_Algorithm_Audit

相反，替代後可能產生新的 CPU/GPU mismatch。資料中的 A100 節點為 8 GPU、128 vCPU；例如每 worker 需要 1 GPU、32 vCPU，即使節點全空，也只能容納四個 workers，而不是八個。resource_shape

所以，**donor pool 的空閒 GPU 數，不能直接當成可供 A10 使用的容量**。多資源配置必須保留；Synergy 的研究也提供了不能只看 GPU 的方法背景。[USENIX](https://www.usenix.org/conference/osdi22/presentation/mohan)

### 必要的約束消融

| 消融世界 | 唯一主要改動 | 能回答什麼 |
|---|---|---|
| **CPU-relaxed** | 忽略 CPU 可行性約束，其餘不變 | CPU 約束在指定策略下是否真正影響等待？ |
| **Node-locality-relaxed** | 同型號資源按總 CPU/GPU 判定，仍保留 gang 與時長 | 節點內共同供應及裝箱限制的聯合代價 |
| **Gang-relaxed** | 相同 workers 可不同時開始，總 workers、需求與每 worker 時長不變 | 同步開始約束的代價 |

Gang-relaxed 必須維持原始 parent job 身份與排序依據，不能把 \(w_j\) 直接改成 1 後少算資源。比較指標使用：

\[
W_j^{\rm ready}=\max_k s_{jk}-a_j,
\qquad
JCT_j=\max_k f_{jk}-a_j,
\]

固定窗口完成數也以全部 workers 完成的 parent jobs 計算。這是離線診斷模型，不是符合原題的可部署方案。

上述診斷可以重疊。即使按等待時間積分，也不能直接相加成一張「原因百分比餅圖」。**它們解釋三項干預的作用機制，不是再加到 \(\phi_C+\phi_B+\phi_S\) 上的額外收益。**

## 2.6 敏感性與「主要原因」的判斷

主矩陣凍結後，再做有限網格：

| 維度 | 建議情景 |
|---|---|
| A10 增容 | \(0,10\%,25\%,50\%,100\%\) |
| 可兼容 A10 作業比例 | \(0,10\%,25\%,50\%,100\%\) |
| 替代時長倍率 | \(0.5,1,1.5,2\) |
| 目的池 | A100；A100＋A800 |
| 群組 | 單／多 worker、原始 duration 分層、原始 GPU 型號 |

非單位時長倍率另報 waiting 和 JCT，稱為**兼容性與性能假設下的端到端效果**，不混入主表的純可達性分解。

兼容集合用固定雜湊和配對種子產生，比例之間盡量巢狀；同時報告兼容作業占比與兼容 GPU-work 占比。不能看完結果才挑「轉出最有利」的長作業。

對「主要由什麼造成」，不要只看某一組 Shapley 排名。增容 100% 與放寬 1% 作業兼容性本來就不是同等強度。建議補充**增容等價量**：

\[
\delta_{\rm eq}(K)
=
\min_{\delta\in\mathcal D}
\left\{
\delta:
Y_A(\mathcal C_\delta,K_0,\pi_0)
\le
Y_A(\mathcal C_0,K,\pi_0)
\right\}.
\]

它回答：

> 在測試網格內，有限兼容性取得的 A10 等待改善，相當於至少增加多少 A10 節點？

這只是測試網格上的比較，必須同時附 donor 代價；固定啟發式不保證曲線單調，不能未驗證就插值出精確最小增容量。

統計上，完整 trace 的配對差是主要證據。不同雜湊種子反映情景選擇的變異，不是新的獨立生產 workload；也不能把 224,112 個排隊相依作業當 IID 樣本。時間 cohort 應從同一連續重播切出，不重設叢集，亦不稱為事後盲測。Q2_正式實驗協議

## 最終應形成的研究結論

這套框架要把三個問題分開回答：

**首先，原始 A10 供給是否不足以實現低等待？**用立即啟動需求、實際排隊過程及增容響應回答，不用完整 GPU-hours／90 天容量比單独下結論。

**其次，不增加物理資源時，有多少等待可透過開放兼容性與既有調度改善消除？**用固定 cohort、共同資源帳本和全因子對照回答，並計入接收池代價。

**最後，剩餘限制具體是什麼？**用 CPU/GPU slots、節點局部性及 gang 消融回答，而不是把所有「有空閒資源但作業沒啟動」統稱為 fragmentation。

就現有證據而言，最值得優先檢驗的工作假說是：**A10 存在實質的隔離池容量壓力，排序又強烈影響等待的分配；原池純 GPU 空間裝箱碎片不是主要解釋，但跨型號轉移後，CPU/GPU 配比和接收池尾部損失可能成為新的限制。**最終的貢獻比例應由上述反事實實驗給出，而不是由這個工作假說預先決定。
