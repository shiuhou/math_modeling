异构 GPU 集群调度优化与跨资源池失衡治理：多维回填、比例匹配放置与技经协同机制研究

2026 MCM Senior Group Problem B（Scheduling a GPU Cluster）全流程数学建模分析报告  |  参赛队伍：Member A, Member B, Member C  |  2026年10月

摘要：针对大规模人工智能计算中心异构 GPU 集群面临的“重尾作业拥塞、多维资源搁浅与跨型号负载极端失衡”三大核心痛点，本文基于阿里巴巴开源集群 90 天真实轨迹数据（包含 4,278 台服务器、10,412 张物理 GPU、632,636 个 vCPU 核心以及 224,112 个非抢占式 Gang-Scheduling 分布式计算作业），开展了从探索性数据诊断、连续时间混合整数规划建模、低复杂度事件驱动调度算法设计到软硬件/金融协同均衡治理的全流程研究。核心研究结论如下：

  • 问题一（数据特征与供需失衡机理诊断）：集群算力需求呈现极端帕累托重尾特征（全体作业 GPU-Hours 的基尼系数高达 Gini = 0.9522，前 1% 的大作业消耗了 43.30% 的总算力时，前 5% 的作业消耗了 87.68% 的总算力时），并伴随显著的日内周期性波动（16:00 峰值到达率为 04:00 谷值的 2.29 倍）及 t = 0 时刻 3,512 个初始积压长作业冲击。跨 GPU 型号供需严重错配：单卡推理/微调池 A10 仅占全集群 GPU 数量的 23.95%（2,494 张），却承载了 49.66% 的作业数与 45.19% 的算力需求（1,111.9 万 GPU-Hours），90 天名义负载率高达 2.064（日均无约束活跃需求达 3,664.0 张 GPU，长期存在约 1,170 张 GPU 的刚性缺口）；而高端 8 卡训练池（A100-SXM4-80GB、H800、GPU-series-2、A800-SXM4-80GB）90 天名义负载率仅为 0.580–0.795，平均超过 2,500 张高端 GPU 处于闲置状态。此外，异构池 GPU-series-1 存在严重的 CPU/GPU 比例失配风险（6.53% 的高 CPU 作业占 19.79% 算力时，若错放至 8 卡 192 核节点将导致单节点 7 张 GPU 被搁浅）。
  • 问题二（已验证的 A10 调度比较）：在完整 111,284 个 A10 作业与统一 shared-timer 配置下，普通 SPT-HOL 的平均等待为 32.906 小时，低于 SPT-FILL 的 34.967 小时；精确作业计数 GPU 容量下界为 22.3179305700 小时。65,536-job 前缀中的 URGENT/TIME/FIXED/FLEX 只作为有明确范围的保护代价分析，不与完整 A10 结果混合。
  • 问题三（技术与金融跨池均衡机制评估）：针对 A10 池的物理容量赤字，本文构建并仿真验证了三类跨池治理方案：（1）带原生保护阈值的跨池弹性溢出（Elastic Overflow）：利用高端池闲置容量吸收单卡 A10 作业，将 A10 平均等待时间降至 4.99 小时（720 张共享卡）及 0.43 小时（1,120 张共享卡）；（2）NVIDIA MIG 硬件虚拟化切分（MIG Partitioning）：从 432 台 A100-SXM4-80GB 节点中划拨 M = 72 台（576 张物理 A100）配置为 3g.40gb（m = 2，新增 1,152 张 40GB 虚拟 A10）或 2g.20gb（m = 3，新增 1,728 张虚拟 A10），在保证剩余 360 台原生 A100 节点零排队延迟（平均等待 0.000 小时，利用率从 62.76% 提升至 75.31%）的前提下，将 A10 平均等待时间分别降至 4.27 小时（中位数 8.0 秒）与 2.55 小时（中位数 0.0 秒）；（3）基于多项 Logit（MNL）离散选择模型的动态拥塞定价机制：对闲置高端池提供 δ = 50% 弹性折扣并对峰值 A10 征收 s = 10% 拥塞附加费，可引导 42.1% 的 A10 作业主动迁移，使 A10 综合平均等待时间降至 1.86 小时，同时盘活闲置高端算力使运营商总营收增长 +13.04%（从 $11.12M 增至 $12.57M）。技术与金融协同设计使全集群 6 大资源池利用率的 Jain 公平性指数从 0.941 跃升至 0.992。

一、 问题一：集群供给结构与多维工作负载特征深度剖析

1.1 异构硬件供给与各型号算力需求宏观对比

数据集涵盖 H = 7,775,878 秒（即标准 90.00 天，TH = 2,160 小时）的作业提交记录。对每个作业 j ∈ J，设其包含 Wj 个同构 Worker，每个 Worker 请求 gj ∈ Z+ 张指定型号 mj 的物理 GPU 与 cj ∈ R+ 个 vCPU，持续运行时间为 dj 秒。作业 j 的总算力需求体积定义为 Aj = Wj gj dj / 3600（单位：GPU-Hours）。对于任意 GPU 型号资源池 m ∈ M，定义其在 90 天周期内的名义 GPU 负载率 ρmGPU 与名义 CPU 负载率 ρmCPU 如下：

1.2 四大核心统计规律与管理洞察

  1. 跨型号结构性冷热失衡（图 1a）：A10 作为高性价比单卡服务器（2,494 台节点均为 1 张 GPU），其总算力需求达 1,111.90 万 GPU-Hours，为 90 天物理可提供上限（538.70 万 GPU-Hours）的 206.4%。即便剔除跨越 90 天边界的尾部剩余时长，A10 在 90 天内的无约束平均并发需求仍达 3,664.0 张 GPU（负载率 146.9%，峰值 4,118 张），存在持续约 1,170 张 GPU 的硬缺口。反观 A100-SXM4-80GB（无约束平均活跃需求 2,318.6 / 3,456 张，占 67.1%，95% 分位需求仅 2,860 张）、H800（平均活跃 1,124.0 / 1,752 张，占 64.2%）、GPU-series-2（64.6%）与 A800-SXM4-80GB（64.3%），四大高端训练池长期保有 30%–40% 的闲置算力余量。
  2. 算力需求的极端帕累托重尾分布与初始积压效应（图 1b, 1d）：全体作业运行时长横跨 1 秒至 15,897,599 秒（184 天）。虽然 50% 的作业运行时长不超过 1,330 秒（22.2 分钟）、75% 不超过 4,887 秒（1.36 小时），但 95% 分位时长跃升至 309.09 小时（12.9 天）。洛伦兹曲线分析表明，全集群作业 GPU-Hours 的基尼系数高达 0.9522（时长基尼系数 0.9580）：前 0.1% 的巨型作业（224 个）消耗了 14.66% 的总 GPU-Hours，前 1.0%（2,241 个）消耗了 43.30%，前 5.0%（11,205 个）消耗了 87.68%，前 10.0% 消耗了 97.11%。此外，在 t = 0 时刻有 3,512 个初始积压/常驻作业同时到达（其中 A10 占 2,102 个，合计 347.09 万 GPU-Hours，占 A10 总需求量的 31.22%）。在传统 FCFS 策略下，这些长达数周的初始大作业将瞬间占满 A10 节点，导致后续成千上万个分钟级短作业陷入长达数十天的排队停滞。
  3. 日内潮汐效应与阶段性到达规律（图 1c）：动态到达作业（t > 0）呈现显著的 24 小时周期性：每日第 16 小时达到提交峰值（累计 13,596 个作业，平均 151.1 个/小时），凌晨第 4 小时降至波谷（累计 5,946 个作业，平均 66.1 个/小时），峰谷比达 2.29 倍。按月度统计，第 1 个月（D0–D29，含初始积压）提交 82,902 个作业（1,267.2 万 GPU-Hours），第 2 个月（D30–D59）与第 3 个月（D60–D89）分别平稳提交 71,184 个（552.9 万 GPU-Hours）与 70,026 个（640.5 万 GPU-Hours）。
  4. 作业粒度分化与多维资源（CPU-GPU）搁浅机理：全集群 90.95% 的作业为单 Worker（Wj = 1），78.42% 的作业请求单卡（gj = 1），而 H800 则以大规模分布式整机训练为主（97.75% 请求 8 卡整机，平均 8.98 个 Worker，最大单作业同时请求 182 个 8 卡节点共 1,456 张 H800，占该池总容量的 83.1%）。更为关键的是，GPU-series-1 虽然总无约束峰值 GPU 需求（1,504 张）小于物理 GPU 总数（1,558 张），但其节点由 901 台 1卡/192核（核卡比 192）、10 台 4卡/192核（核卡比 48）与 77 台 8卡/192核（核卡比 24）混编而成。若放置算法未能识别核卡比，将低 CPU 作业（cj ≤ 24，占该池 74.3%）优先放入 1 卡节点，则后续 630 个高核卡比作业（cj / gj > 24，最高达 1 卡配 192 核，占该池 19.79% 算力时）被迫放入 8 卡节点时，单个 1 卡 Worker 即可耗尽整台 8 卡节点的 192 个 vCPU，直接导致该节点剩余 7 张物理 GPU 被完全搁浅（Resource Stranding）！

二、问题二：容量有效的调度比较与方法收敛

2.1 模型与策略定义

每一种 GPU 型号作为独立资源池分析。作业 j 具有提交时刻 rj、时长 pj、Worker 数 wj、每 Worker 的 GPU 请求 gj 与 CPU 请求 cj。作业在 sj ≥ rj 时启动，并在 sj+pj 完成，所有 Worker 必须同步启动。对节点 i，合法放置必须同时满足 gjxj,i ≤ Gifree(t)、cjxj,i ≤ Cifree(t) 以及 ∑ixj,i=wj。模拟器使用非抢占、精确整数秒时长和原子 gang 放置。

普通 SPT-HOL 按 (pj,rj,job_id) 排序已到达作业；它没有 aging threshold、urgent promotion 或 reservation。队首不可放置时，该决策时刻停止启动。SPT-FILL 使用相同的时长优先顺序，但可继续检查后方当前可行作业。因此普通 SPT-HOL 不含 168 小时 aging。SPT-URGENT-HOL/TIME/FIXED/FLEX 另行加入 aging/reservation 机制，本节只在已验证的 65,536-job 前缀中报告。

正式 A10 运行共同使用 FF-id、shared-timer、K=200、θ=604800 秒、H=7,776,000 秒和完整排空。168 小时是探索性门槛，不是最优参数；事件模式是独立的实验配置，不由策略名称暗示。

2.2 作业计数容量下界与精确分解

对 A10 容量 C=2494，作业总 GPU 宽度为 Gj=wjgj，定义 Z(t)={j:rj≤t<rj+pj}。令 q(t) 为从 Z(t) 删除最少作业，使剩余 GPU 宽度不超过 C，则 Lcount=∫q(t)dt/(3600N) 是普通平均等待的容量松弛下界。计算使用半开区间的精确事件积分与整数 GPU 宽度直方图，没有使用时间网格。

证明中令 S(t) 为实际服务集合，A(t)=S(t)∩Z(t)。延后启动的作业可能在 rj+pj 之后仍在运行，因此不能写成 S(t)⊆Z(t)；但 Z(t)\\A(t) 是合法删除集合，故 ∑min(Wj,pj)≥∫q(t)dt，进而 ∑Wj≥∫q(t)dt。例如 (r,p,s)=(0,2,4) 的作业在 t=5 属于 S(t) 但不属于 Z(t)。

非抢占作业满足精确恒等式 Wj=min(Wj,pj)+max(Wj-pj,0)。因此报告 Capacity LB、Within-window Gap 与 Beyond-duration Waiting；三者是围绕 GPU 容量松弛的描述性记账，不是因果贡献或距离最优排程的精确距离。

2.4 65,536-job 保护策略范围分析

同一计数下界在已验证 65,536-job A10 前缀为 24.9181888580 小时。普通 FILL/HOL 平均等待为 31.042/30.332 小时。保护策略分别为：URGENT-HOL 556.492 小时、URGENT-TIME 350.528 小时、URGENT-FIXED 350.088 小时、URGENT-FLEX 349.715 小时；FIXED/FLEX 分别接纳 62/133 个 crossing。它们相对 TIME 的平均下降只有 0.439/0.813 小时，且同时存在改善与恶化作业。这些是 65k 探索性门槛结果，不能混作完整 A10 结果。

2.5 方法选择与范围

以已验证 A10 的普通平均等待为目标，普通 SPT-HOL 是当前主候选：它比 SPT-FILL 简单，并在 65k 前缀与完整 A10 中均有较低平均等待。SPT-FILL 仍适合作为偏好单 Worker 即时启动的对照；保护策略可作为特定尾部保护偏好的实验备选，但目前的平均等待代价和额外证据处理成本不足以支持将其作为默认方法。

证据范围仅为 A10，并非完整 224,112-job 集群。Urgent 全量、1350 小时、EASY-NR、Q3 和新的正式排程运行均未执行。全部数值、hash、archive、命令与验收状态见 results/20261016-b-q2-m2g-01/。

三、 问题三：消除跨 GPU 型号失衡的技术与金融协同治理方案

3.1 技术路径：跨型号弹性溢出（Elastic Overflow）与 NVIDIA MIG 硬件切分

问题二的已验证证据仅覆盖 A10 资源池，并不证明跨池迁移或捐赠容量可行。A10 的 Q1 需求—容量诊断提供了跨池方案的研究动机，但时序、节点放置、CPU 兼容性和服务影响仍需独立验证。因此，本节的跨池技术与金融表格继续作为研究候选，相关实验均标记为 NOT_RUN：

  1. 方案 3A（带原生保护阈值的跨池向上兼容弹性溢出）：由于全部 111,284 个 A10 作业均请求单卡（gj = 1，显存需求 ≤ 24GB），它们在架构上完全向上兼容空闲的高端 80GB GPU（A100、A800、GPU-series-2、H800）。为确保高端池原生多卡大作业不受干扰，我们设立 15% 原生安全预留阈值：仅当捐赠池空闲 GPU 比例超过 15% 时，才动态借出闲置 GPU 承载排队中的 A10 作业。我们同时评估了保守无加速场景（κ = 1.00）与基于 FP16 算力/显存带宽及 Amdahl 定律标定的硬件加速场景（κ = 1.45）。
  2. 方案 3B（基于 NVIDIA MIG 硬件虚拟化的节点重构）：将整张 80GB A100 物理卡分配给单个 A10 Worker（平均仅需 7.13 个 vCPU）会造成显存与算力的浪费。利用 NVIDIA Multi-Instance GPU (MIG) 硬件分区技术，我们将 M ∈ {48, 64, 72} 台长期闲置的 A100-SXM4-80GB 节点（占 432 台总数的 11.1%–16.7%）重构为虚拟 A10 节点：（a）MIG-2x 模式（3g.40gb）：每张物理 A100 切分为 2 个独立 40GB 硬件实例（单节点提供 16 张虚拟 GPU 与 128 个 vCPU）；（b）MIG-3x 模式（2g.20gb）：每张物理 A100 切分为 3 个独立实例（单节点提供 24 张虚拟 GPU 与 128 个 vCPU）。仿真引擎严格执行每台物理服务器 128 个 vCPU 的总上限约束。

在商业云平台场景下，管理者还可通过价格杠杆引导弹性用户主动切换 GPU 型号。参照阿里云/AWS 公开目录价格（A10 为 $1.00/GPU-h，GPU-series-1 为 $1.20，GPU-series-2 为 $2.20，A800 为 $3.20，A100 为 $3.50，H800 为 $4.80；折算加速比或 MIG 实例后的替代池基准等效单价为 palt = $2.40/h），当运营商对闲置高端池提供折扣率 δ ∈ [0, 60%] 并对拥塞 A10 池征收峰值附加费 s ∈ [0, 15%] 时，基于随机效用理论的多项 Logit（MNL）模型给出作业 j 的自愿迁移概率为：
