# B 題研究計劃：GPU 叢集調度與資源失衡

## 研究目的

本計劃用來指導團隊研究，不代替團隊完成模型、實驗或競賽論文。它規定要回答的問題、要取得的證據、候選方法的選擇方式，以及各階段的驗收條件；不預先指定最終演算法，也不把任何性能改善寫成既定結論。

整體研究目標是：在題目給定的資源與限制下，識別等待與型號失衡的來源，選擇或設計可解釋的調度方法，並用一致的實驗比較效率、公平性和計算代價。

研究依據依序為官方 B 題 PDF、競賽 CSV、提交指南、團隊既有工程規範與深度研究資料。現有研究報告與先前計算可作為參考，但不能替代團隊對資料、程式與結論的核驗。

---

## 一、先把題目轉成研究問題

| 研究問題 | 需要弄清楚什麼 | 對應題目 |
|---|---|---|
| RQ1：工作負載與容量如何匹配？ | 哪些作業消耗資源；需求如何隨時間與型號變化；作業數與工作量是否給出不同判斷 | 第一問 |
| RQ2：等待從哪裡來？ | 容量壓力、隊首阻塞、CPU/GPU 配比、同步啟動及放置策略各有什麼影響 | 第一、二問 |
| RQ3：如何改善效率而不忽視部分作業？ | 排序、回填、等待保護與放置的收益及代價；不同作業群組是否受益或受損 | 第二問 |
| RQ4：何時值得跨型號調配？ | 兼容性、替代後時長、接收池負擔與額外假設如何影響替代價值 | 第三問 |

不要把研究問題寫成「證明 A10 一定因為碎片化而擁堵」或「證明新演算法比所有基線好」。應允許資料否定初始假說。

## 二、階段一：題面核對與研究邊界

### 要做的工作

逐句閱讀官方題面，把要求分為硬約束、可自行設計的部分及資料缺口。建立一張題目—模型—驗證對照表，供程式、數學模型和寫作共同使用。

已知的關鍵題面條件包括：同一作業的 workers 相同且同步開始；每個 worker 的 CPU/GPU 需求由同一節點滿足；每節點容量不可超額；原始設定按 GPU 型號匹配；作業不可搶佔；時間零全部節點空閒；duration 在作業提交時已知。

因此，時長預測不是必需的前置研究。團隊應另外明確採用線上還是離線決策；若採線上，策略只接收已到達作業及其已知時長，不能提前讀取未來到達作業。

### 本階段要回答的問題

CPU/GPU 請求是每 worker 還是全作業？worker 可否跨節點拆分？第三問究竟修改哪一項假設？哪些資訊在決策時已知？題目未提供哪些真實系統資訊？

### 交付與驗收

交付一份精簡資料／模型契約，以及三問對應的研究問題。所有隊員使用相同定義；自行引入的假設與官方要求分開記錄。若尚不能一致解釋一個小作業如何分配資源，不進入複雜演算法設計。

## 三、階段二：資料研究與瓶頸假說

### 3.1 先核查資料，再討論規律

檢查欄位、單位、唯一識別碼、缺失值、重複值、非正時長、CPU 小數與零請求、GPU 型號一致性，以及作業在空叢集上的基本可放置性。原始資料保持不變；任何轉換、排除或修正都必須有理由和紀錄。

時間欄位先確認精度。資源計算不得為實作方便任意取整。沒有合法放置的作業也不能被靜默刪除，應先查明是輸入問題、語義誤讀還是模型錯誤。

### 3.2 EDA 應圍繞問題組織

| 分析面向 | 建議檢查 | 希望支持的研究決策 |
|---|---|---|
| 到達過程 | 日／週作業數、突發批次、不同型號時間變化 | 選擇代表性測試區間與負載情景 |
| 作業形狀 | worker 數、每 worker CPU/GPU、總 GPU 需求 | 判斷同步啟動及放置是否值得深入 |
| 執行時長 | 分位數、累積分布、長短作業差異 | 決定是否需要時長感知排序與長作業保護 |
| 工作量 | 每作業 GPU-hours、集中度、型號工作量 | 區分「作業很多」與「資源消耗很大」 |
| 節點配置 | 每型號節點數、GPU 數、CPU/GPU 比例 | 分析可用容量與節點資源形狀 |
| 時間邊界 | 初始批次、窗口外仍執行的長作業 | 制定初始狀態、固定窗口與排空規則 |

工作量可用 worker 數 × 每 worker GPU 數 × duration 計算，但它不是硬體實際運算量的量測值。完整生命週期工作量／提交窗口容量也不是實測分配率；存在跨窗口作業時，比值大於一不能單獨證明窗口內一直擁堵或穩態不穩定。

### 3.3 建立可被否定的假說

| 候選假說 | 需要取得的證據 | 不成立時如何調整 |
|---|---|---|
| 型號間存在重要供需失衡 | 時間變化、容量比較與模擬等待同時支持 | 不把型號失衡當作第二問唯一主線 |
| 隊首阻塞造成可避免的等待 | 比較嚴格排隊、可行作業選擇與回填 | 降低回填模組的優先級 |
| 節點資源形狀限制啟動 | 檢查總量看似足夠、但逐節點不可放置的狀態 | 不增加複雜碎片化分數 |
| 時長排序與極端等待有取捨 | 同時比較平均、尾部、最大等待與時長群組 | 不預先指定長作業保護必然有益 |
| 跨型號替代能改善整體效果 | 等待節省超過執行代價，且接收池退化可接受 | 縮小替代範圍，或只報告適用邊界 |

本階段的成果不是一堆圖，而是一份「目前知道什麼、尚不能知道什麼、下一步應驗證什麼」的證據摘要。

## 四、文獻研究：用適配性篩選，不繼續堆方法名稱

先使用已有深度研究報告中的文獻作候選，集中查核四類：非搶佔排序、同步作業回填、多資源放置，以及異構硬體效能與兼容調度。

每篇只需回答：它解決什麼瓶頸？是否假設可搶佔？是否知道執行時長？是否允許改變 worker 數？是否需要本題沒有的拓撲或效能資料？哪一部分能轉化成可驗證的候選方法？

需要搶佔、彈性擴縮、額外顯存／網路資訊或未知時長預測的方案，不直接搬入主模型。可以借鑑思想，但必須說清改造後的假設與功能。

交付一張精簡方法適配表和必要的原始文獻資訊。只保留會影響方法選擇、評估口徑或假設正當性的資料；不以文獻數量作進度。

## 五、階段三：建立共同模型與可信實驗平台

### 5.1 數學模型要先回答的問題

明確作業、節點、時間、開始時刻、資源配置和可用資訊。將同步啟動、逐節點 CPU/GPU 容量、型號匹配及不可搶佔轉成約束。因同作業 workers 相同，可先研究簡潔的 worker 數量表示法，不急著建立龐大的逐 worker 二元變數模型。

先說清主要目標與保護指標，例如在控制極端等待退化的前提下改善平均響應。不要一開始把許多互不相同的指標加權成沒有解釋的總分。

### 5.2 模擬器與策略分開

模擬器負責到達、完成、資源狀態和時間推進；策略負責從已到達等待作業中選擇啟動對象及其放置。所有方法共用同一套容量規則、事件順序、初始狀態和評價器。

同時刻事件順序與半開區間佔用語義要寫清。放置必須先驗證完整計畫再一次提交，失敗不能留下部分配置。若採等待門檻，還要決定門檻跨越時是否額外觸發調度。

### 5.3 驗證先於優化

用可手算案例驗證單 worker、多 worker 同步啟動、節點內需求、型號限制、小數與零 CPU、完成釋放、同時到達／完成，以及放置失敗不改狀態。

隨後增加小規模隨機案例與獨立資源帳本回放。從小資料逐步擴展到完整 trace，量測耗時、記憶體與瓶頸。不要因為某個版本能輸出數字，就認定模擬器已經可信。

### 5.4 基線選擇與定義

候選基線包括 FCFS、已知時長 SJF、允許尋找下一個可行作業的排序版本，以及具有明確預約規則的回填。第一輪不必全部完成，但進入「改進有效」的判斷前，應有一個強且公平的比較對象。

每種方法都要記錄：隊首不可放置時是否阻塞；不同型號是否獨立排隊；同時到達如何平手排序；節點如何選擇；回填保護哪個預約。不能把不同實作都模糊稱為 FCFS、SJF 或 EASY。

### 本階段驗收

手算案例與資源檢查通過；各基線共用一致環境；完整 trace 可以完成並量到成本；沒有靜默丟作業、超額分配或截掉慢作業。未達此條件時，暫停增加主算法模組，先修正平台或縮減實作範圍。

## 六、階段四：根據證據選擇改進方向

最終方法在基線研究後決定，而不是現在直接指定 BCAF、AGDB、強化學習或某個加權公式。

| 實驗顯示的主要問題 | 優先探索的改進 | 必須同時檢查的代價 |
|---|---|---|
| 可運行的小作業被隊首擋住 | 預約式回填或可行候選選擇 | 受保護作業是否被延後、預約運算成本 |
| 短作業優先使部分作業極端延後 | 等待老化、保護集合、排序與公平性折衷 | 平均等待與固定窗口完成數是否退化 |
| 多資源放置限制啟動 | Best-Fit、資源形狀感知放置 | 是否只改善代理分數而未改善真實指標 |
| 不同型號表現差異明顯 | 按池檢驗策略適用範圍 | 額外參數與過度調整的風險 |

建議第一輪限制為一個基礎方法和一至兩個有明確假說的改進。每個新增模組都要能回答：改變了哪個決策？預期改善什麼？需要什麼新增假設？如何透過消融否定它？

先比較單一改進，再評估組合。若沒有穩健收益或代價超過事先約定的範圍，移除該模組。不因投入了時間就把它保留在主模型中，也不預設所有指標都應同時勝出。

研究成果是一份方法取捨：保留什麼、淘汰什麼、依據是什麼，而不是事後替既定方案尋找理由。

## 七、階段五：第三問的研究路線

### 7.1 先判斷哪些假設可取得證據

檢查資料是否提供兼容性、替代型號執行時間、分割單元效能或價格行為資訊。沒有的內容應列為缺口，不直接從 GPU 名稱、理論算力或其他叢集的性能數字推得。

第三問可比較跨型號替代、虛擬分割與定價誘因的資料需求及實作成本，再選一條作為正式研究。其餘方向可作討論，不要求全部落地。

### 7.2 優先候選：未啟動作業的跨型號替代

若選這條路線，需要明確定義可兼容作業集合、替代後時長、worker 與 CPU/GPU 需求是否改變，以及接收池原生作業如何被保護。

核心問題是：等待節省是否超過執行時間代價？改善是否只是把擁堵從原池移到接收池？當兼容比例或速度倍率改變時，結論在哪裡失效？

參數須來自題面、可適用的外部實測或清楚標示的情景假設。固定情景與抽樣規則後再比較策略，不按結果反覆挑選最有利的兼容集合。

### 7.3 虛擬化與定價的研究條件

研究虛擬化前，先核對目標硬體支援、隔離機制、資源單元與速度假設；不能把分割直接視為物理算力增加。研究定價前，先分清內部稀缺度分數與真實客戶反應；缺少支付意願資料時，後者只能作額外假設。

### 本階段驗收

至少完成一條有明確假設、可評估且同時觀察原池與接收池的路線。若數據不足以識別真實性能，就交付適用條件與敏感性邊界，不虛構已校準的替代矩陣或價格彈性。

## 八、實驗協議：在看改進結果前確定

### 指標與評估對象

主指標應由研究目標選出，保護指標覆蓋尾部／最大等待、長作業群組與固定窗口完成數。GPU/CPU 分配率用容量時間加權；它不是硬體核心的實際利用率。必要時加入 slowdown，但不能用它取代絕對等待。

至少按 GPU 型號、作業大小與 duration 分層，以免全體平均掩蓋某一群組退化。資料不包含的使用者或組織資訊，不構成可量測的公平性維度。

### 時間窗口

分開定義固定窗口完成數／分配率，以及全部到達作業的等待／JCT。最後一次到達後是否排空、哪些作業納入統計，都在比較前約定。慢作業不能因為尚未完成而被排除。

切分時間段時，不可每天重設空叢集來消除跨日積壓。不同策略應從相同原始初始條件重播，按一致規則評估。

### 調參與結果使用

預先限定候選參數、開發範圍與主要比較。完整 trace 已在前期討論中被探索過，不能把其中一段事後稱為從未看過的獨立測試集。後續時間分段應清楚稱為內部穩健性研究；若需要真正獨立的泛化結論，須另取得未使用資料或明確的獨立生成情景。

確定性重播不因重複執行就增加獨立樣本。若方法或兼容集合有隨機性，再用配對種子比較；不要把有隊列相依性的所有作業當成 IID 樣本來製造顯著性。

### 消融、壓力與下界

消融用來確認新增模組是否有獨立貢獻；負載、容量、初始批次和平手排序敏感性用來檢查結論範圍。小規模精確最佳化可作補充，但必須區分已證最優解、超時可行解與下界。

約束放鬆實驗應稱為指定條件下的反事實比較。不同放鬆順序或策略可能給出不同效果，不能未經論證就稱為唯一的因果佔比。

## 九、計算資源計劃：7×4090 如何納入

先盤點伺服器 CPU、RAM、可用進程、既有環境與正在運行的工作，並在授權範圍內量測原型。不要把 GPU 張數當成模擬器速度的保證。

計算順序為：手算案例 → 小型可驗證資料 → 代表性區間 → 完整 trace → 凍結後的正式比較。只有量測發現瓶頸後，才決定是否需要索引、向量化、編譯加速或並行實驗。

七張 4090 暫列為可選資源：主研究穩定後，可考慮小型真實多 GPU 作業驗證，或有明確假說的學習型方法探索。不能為了使用 GPU 而加入新的模型，也不能用同型號 4090 實驗直接識別 A10 與 A100 間的效能比。

實機補充必須清楚說明它驗證的是機制、開銷還是性能，並與固定 duration 的 trace 模型區分；不放進前期基線交付的關鍵路徑。

## 十、團隊協作與分工

可按實際人數安排三條工作線，而不是讓每人各寫一套完整解法。

| 工作線 | 責任 | 與其他人的介面 |
|---|---|---|
| 資料與問題診斷 | 資料契約、EDA、瓶頸假說、缺口與限制 | 輸出可追溯的統計與待驗證問題 |
| 模型與演算法 | 數學約束、方法比較、候選設計與假設 | 使用共同模擬器與策略介面 |
| 實驗與論證 | 正確性驗證、共同評價器、消融、計算成本、研究敘事 | 審核數字能否支持對應主張 |

指定一位整合負責人維護題目語義、實驗口徑和方法取捨。沿用既有 feat 分支與審查方式；共用模擬器、共用指標，不各自維護近似但不一致的版本。

依現有工程規範維護一份活動計劃與簡短決策紀錄。正式研究資料、必要測試及關鍵結果保留；不為每輪新增重複日報、狀態文件或框架。

## 十一、倒排里程碑與收斂條件

以下按約六天研究窗口安排，實際日期與交付節奏由團隊調整，不是運行時間承諾。

| 階段 | 主要目標 | 驗收／收斂條件 |
|---|---|---|
| 第 1 天 | 題面契約、資料核查、核心 EDA、手算案例與原型 | 知道哪些假說值得研究，沒有語義分歧 |
| 第 2 天 | 可信基線、共同指標、完整 trace 可行性與成本 | 若平台未通過驗證，暫停增加複雜方法 |
| 第 3 天 | 選擇一條主改進方向，對照基線 | 沒有證據的模組降級或移除 |
| 第 4 天 | 第三問的一條可評估路線，確認主方法 | 凍結主要架構，不再新增大型研究方向 |
| 第 5 天 | 消融、敏感性、分層結果與失效邊界 | 每個主張有對應證據；保留不利結果 |
| 第 6 天 | 可重現性核查、結論與限制整理、論文收斂 | 數字與程式一致，分清實測、假設與未驗證項 |

寫作可同步記錄題意、模型定義和實驗協議，但摘要中的成果與結論要等證據形成後再寫。此計劃本身不是提交稿。

## 十二、當前先下發的研究任務

**第一個任務包只要求：**閱讀原題與現有工程，建立約束／數據契約；提出少量可證偽的瓶頸假說；定義共用模擬與評價規則；規劃並建立經過手算驗證的最小基線；列出候選路線、資料缺口及驗收條件。

此階段不要預設最終算法，不要承諾改善百分比，不要先寫論文摘要，不要自動展開所有高階方法，也不要因服務器有七張 GPU 就引入神經網絡。

對團隊成員或編碼助手的研究要求是：每個新增模塊先說明它回答的研究問題、使用的資訊、必要假設、對照方法及失敗時的收斂方案。先審查既有實現與規範，復用可用部分，不覆蓋其他成員修改；本計劃不自動授權遠端部署、權限更改或破壞性操作。

第一輪研究討論應回答的是：**題目邊界是否明確、哪些問題有證據值得追、實驗是否可信，以及下一步應選擇哪條路線。**
