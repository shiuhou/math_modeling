## 摘要

本題研究異構 GPU 叢集中，持續到達的多 worker 作業如何排隊、同步啟動和放置。每個 worker 必須在同一節點取得所需 GPU 與 vCPU；同一作業的 workers 完全相同，且必須同時開始。作業執行時間在提交時已知，啟動後不得搶佔。研究必須同時回答資料規律、調度與放置設計，以及 GPU 型號之間的供需失衡三個問題。[P，第 1–2 頁]

本次重新核算競賽資料，共有 **224,112 個作業、4,278 個節點、10,412 張實體 GPU、632,636 vCPU 與 6 種 GPU 型號**。提交窗口約 90 天，但最長作業持續約 184 天。作業時長中位數僅 1,330 秒，前 1% 作業卻佔全部請求 GPU 工作量的 43.31%，顯示極強的工作量集中現象。

本次亦完成完整 trace 的兩個初步基線：按型號分池的 FCFS，以及嚴格短作業優先 SJF-HOL；兩者均採確定性的 First-Fit 節點放置。全體平均等待由 FCFS 的 **446.97 小時**降至 SJF-HOL 的 **16.36 小時**，但最大等待由 **1,423.25 小時**增加至 **3,017.29 小時**，全部作業完成時刻由第 **243.26 天**延至第 **309.72 天**。這不是某個新演算法的成果，而是已完成的基線對照，揭示「平均效率與極端等待不能用同一個數字概括」。[C1–C2]

因此，本文建議主方法採用**等待老化保護、已知時長排序、資源預約與 gang-aware 回填**，再透過明確兼容性與速度倍率假設，評估未啟動作業的跨 GPU 型號替代。研究重點應是識別可由排序改善的等待、必須由容量或兼容性改變才能處理的限制，以及效率改善對長作業的代價。

**完成狀態：** 題面核驗、資料核算、兩個完整基線及相應驗證已完成；改進調度器、正式 EASY/SJF-fit 強基線、跨型號替代、消融與敏感性實驗尚未完成。本文對後者提供明確模型與實驗方案，不預填性能結果。所有已列數字來自本次 ChatGPT 分析環境，並非使用者 7×4090 伺服器的實測。

## 一、研究依據與證據邊界

### 1.1 資料來源的優先順序

本文以官方賽題 PDF 為規則依據，以競賽 ZIP 裡的 CSV 為實驗輸入。先前的 `deep-research-report-topicB.md` 是方法參考，不替代原題。外部文件只用來說明回填、異構效能及 MIG 等概念，不將外部 trace 的額外欄位、機制或性能數字拼回競賽資料。

原題說明資料改編自 Alibaba Cluster Trace，僅保留前三個月的作業提交，移除組織與原始優先級資訊，並刪除非整數 GPU 請求的作業。[P，第 1 頁] 對應的公開來源是 `cluster-trace-v2026-spot-gpu`，不是同倉庫另一份涵蓋更大叢集的 GPU v2026 資料。[W1]

### 1.2 相較先前深度研究，需要明確修正的四點

**第一，執行時長不是未知量。** 原題明確給定 `duration` 在提交時已知。因此，本題可合法使用已到達作業的真實時長，不必將 SJF 降為 Oracle，也不需要把時長預測器放進主要交付路線。但尚未到達的作業仍不應提供給本文採用的線上策略。[P，第 1 頁]

**第二，同一作業內 workers 相同。** 單一作業在當前資源上能否放下，可以直接計算可容納 worker 數；不能把一般異質 worker 裝箱問題的困難，直接套在這個已簡化的子問題上。

**第三，完整作業工作量／90 天容量不是實測利用率。** 因為部分作業延續到 90 天之外，該比值大於 1 不能單獨證明穩態不穩定或嚴重排隊。本次 `GPU-series-1` 的例子會具體展示這一點。

**第四，bounded slowdown 必須保留下界 1。** 本文使用 `max(1, JCT/max(duration, tau))`。省略最外面的 `max(1,·)`，會讓極短且無等待的作業得到小於 1 的值；後續若使用其倒數分析公平性，也會產生不必要的解釋問題。

### 1.3 三類陳述必須分開

| 類型 | 本文例子 | 可否視為已驗證成果 |
|---|---|---|
| 題面規定 | 初始全空閒、不可搶佔、提交時已知 duration | 是，來自原題 |
| 本次計算 | 資料筆數、工作量集中度、FCFS/SJF-HOL 結果 | 是，限定本次模型與輸入 |
| 本文研究方案 | AGDB 改進器、替代比例、速度倍率、保護門檻 | 否，須後續實驗 |

## 二、題目介紹與三問拆解

### 2.1 背景與核心矛盾

不同節點搭載不同 GPU 型號、不同 GPU 數量與 vCPU 容量。作業到達後，不只要決定「先跑誰」，還要決定「每個 worker 放在哪」。即使整個叢集的空閒 GPU 總數很多，仍可能因型號不匹配、CPU 不足或單一 worker 不能跨節點拆分，而無法啟動特定作業。[P，第 1–2 頁]

這個問題應建模為：**按時間到達、不可搶佔、同作業 workers 同步啟動、CPU/GPU 共同約束的異構資源調度問題。** 不需要額外假設網路拓撲、顯存限制或模型訓練內容，因為題目資料沒有提供這些資訊。

### 2.2 第一問：理解資料

第一問要求回答作業如何到達、偏好哪些 GPU、作業大小與時長如何變化、需求是否隨時間改變，以及少數大作業是否佔據大量計算工作。應把作業數、GPU 數與 GPU 工作量分開：一個短作業和一個持續數月的作業，在作業數統計中各佔一筆，但對資源的影響完全不同。[P，第 2 頁]

建議交付四類內容：資料契約與品質檢查、按型號的供需表、時長／規模／工作量分布，以及日或週級的到達變化。每張圖都應對應一個管理或建模問題。

### 2.3 第二問：調度與放置

第二問必須同時完成排隊策略與 worker 放置。硬約束包括：同作業全部 workers 同時啟動、每個 worker 的 CPU/GPU 必須來自同一節點、逐節點容量不可超額、型號匹配、不可搶佔，以及時間 0 全部節點空閒。[P，第 2 頁]

評價不能只比較平均等待；題目明確允許比較中位數、P95 或最大等待、GPU/CPU 分配率、固定時間內完成數、公平性及調度運算成本。[P，第 2 頁]

### 2.4 第三問：減少 GPU 型號失衡

第三問要求提出並評估一種或多種失衡緩解方式。跨型號替代、高階 GPU 分割，以及價格誘因都只是可選方向，不必全部實作。題目也明確提醒：資料沒有實際價格或支付意願；採用定價或替代時，必須說明額外假設。[P，第 2 頁]

本文優先研究「尚未啟動作業的兼容型號替代」，因為它能與第二問共用同一個模擬器。已運行作業不遷移、不重啟、不改型號，以維持原有不可搶佔約束。

## 四、資料分析方法與實際計算

### 4.1 作業資源需求與工作量

對作業 \(j\)，記 worker 數為 \(w_j\)、每 worker GPU 為 \(q_j\)、每 worker vCPU 為 \(c_j\)、執行秒數為 \(p_j\)。

\[
G_j=w_jq_j,\qquad C_j=w_jc_j.
\]

完整 GPU 工作量與 CPU 工作量分別是：

\[
H_j^G=\frac{w_jq_jp_j}{3600},\qquad
H_j^C=\frac{w_jc_jp_j}{3600}.
\]

例如 4 個 workers、每個需要 2 張 GPU 及 16 vCPU、執行 3,600 秒，對應 8 張 GPU、64 vCPU，及 8 GPU-hours、64 vCPU-hours。這只是計算示例，不是挑選出的實驗作業。

### 4.2 按 GPU 型號的規模與工作量

| GPU 型號 | 節點數 | GPU 數 | 作業數 | GPU 工作量（小時） | 工作量／窗口 GPU 容量 |
|---|---:|---:|---:|---:|---:|
| A10 | 2,494 | 2,494 | 111,284 | 11,118,976.35 | 2.064 |
| A100-SXM4-80GB | 432 | 3,456 | 80,877 | 5,935,901.84 | 0.795 |
| A800-SXM4-80GB | 22 | 176 | 3,959 | 232,378.23 | 0.611 |
| GPU-series-1 | 989 | 1,558 | 9,643 | 3,891,640.36 | 1.156 |
| GPU-series-2 | 122 | 976 | 13,633 | 1,223,765.15 | 0.580 |
| H800 | 219 | 1,752 | 4,716 | 2,203,214.49 | 0.582 |

本表的窗口容量均以 \(T=7,775,878\) 秒計算。全部作業的完整 GPU 工作量為 **24,605,876.43 GPU-hours**；全部 vCPU 工作量為 **646,986,320.49 vCPU-hours**。[C1]

定義：

\[
\rho_g^{work}=
\frac{\sum_{j:g_j=g}w_jq_jp_j}
{T\sum_{m:g_m=g}G_m}.
\]

**重要口徑：\(\rho_g^{work}\) 不是資源分配率，也不是已估計出的平穩到達強度。** 它表示在這個提交窗口收到的作業，其完整生命週期工作量相對窗口容量有多大。大量作業會跨越窗口，因此比值大於 1 並不等於窗口內每刻都擁堵；比值小於 1 也不排除局部突發或裝箱阻塞。

### 4.5 A10 的結構特徵

A10 有 2,494 個節點且每節點只有一張 GPU。其中 2,492 個節點有 128 vCPU，另外 2 個有 126 vCPU。全部 A10 workers 都要求一張 GPU；約 **99.29% 的 A10 作業只有一個 worker**。[C1]

## 五、數學模型與計算下界

### 5.1 記號與資訊條件

作業集合為 \(\mathcal J\)，節點集合為 \(\mathcal M\)。作業參數為 \((a_j,p_j,w_j,q_j,c_j,g_j)\)，節點參數為 \((G_m,C_m,g_m)\)。決策變數 \(s_j\) 為作業開始時間，\(n_{jm}\in\mathbb Z_{\ge0}\) 為作業 \(j\) 放在節點 \(m\) 的 worker 數。

同作業 workers 相同，所以使用整數 worker 計數就足夠，不必為每個相同 worker 增加一個二元變數。完成時刻：

\[
b_j=s_j+p_j.
\]

本文選擇線上決策：時刻 \(t\) 的策略只使用已到達作業、其已知時長和當前叢集狀態。原題沒有要求訓練任何預測模型；把全部未來作業提前送入決策器，則是不同的離線問題，必須另外標示。

### 5.2 硬約束

\[
s_j\ge a_j,\qquad \sum_m n_{jm}=w_j.
\]

\[
g_m\ne g_j\Longrightarrow n_{jm}=0.
\]

任意時刻 \(t\) 與節點 \(m\)：

\[
\sum_{j:s_j\le t<b_j} q_jn_{jm}\le G_m,
\]

\[
\sum_{j:s_j\le t<b_j} c_jn_{jm}\le C_m.
\]

同一作業只有一個 \(s_j\)，因此所有 workers 同步開始。\(n_{jm}\) 在整個 \([s_j,b_j)\) 區間內固定，表達不可搶佔、不中途改變放置。採用半開區間，完成時刻釋放的資源可以立即供同一時刻的新作業使用。

### 5.3 單一作業的精確可放置判定

若節點當前剩餘資源為 \(F_m^G(t),F_m^C(t)\)，定義：

\[
h_{jm}(t)=
\begin{cases}
0,&g_m\ne g_j,\\
\left\lfloor F_m^G(t)/q_j\right\rfloor,&g_m=g_j,\ c_j=0,\\
\min\left\{\left\lfloor F_m^G(t)/q_j\right\rfloor,
\left\lfloor F_m^C(t)/c_j\right\rfloor\right\},&g_m=g_j,\ c_j>0.
\end{cases}
\]

則在題目沒有額外拓撲或同機限制的前提下：

\[
\boxed{j\text{ 現在可啟動}\iff \sum_m h_{jm}(t)\ge w_j.}
\]

必要性由逐節點容量得到；充分性是把相同 workers 依序分配到最多 \(h_{jm}\) 個位置，直到全部放完。這是精確判定，不是啟發式。它也自然處理 CPU 請求為 0 的邊界情況。

### 5.4 為什麼整體調度仍然困難

單作業判定容易，不代表多作業整體排序容易。考慮一個特殊情況：所有作業時間 0 到達、每作業只需要一張 GPU、有 \(m\) 個各一張 GPU 的節點，CPU 永遠足夠。若執行時長取 3-PARTITION 的數字 \(a_i\)，總和為 \(mB\)，且每個 \(a_i\in(B/4,B/2)\)，那麼能否在 \(B\) 時間內完成全部作業，就等價於能否把數字分成 \(m\) 組、每組總和為 \(B\)。

因此，廣義輸入下的整體最小化完工時間問題包含強 NP-hard 的特殊情況。但這不是宣稱「對當前 CSV 做一次單作業放置判定也需要 NP-hard 求解」。

### 5.5 工作量與到達時間下界

在不允許跨型號替代時，每個 GPU 池的完工時間 \(M_g\) 必須滿足：

\[
M_g\ge\max\left\{
\frac{\sum_{j:g_j=g}w_jq_jp_j}{\sum_{m:g_m=g}G_m},
\frac{\sum_{j:g_j=g}w_jc_jp_j}{\sum_{m:g_m=g}C_m},
\max_{j:g_j=g}(a_j+p_j)
\right\}.
\]

這些下界都從時間 0 起算。第一、二項分別來自 GPU／CPU 工作量守恆；第三項來自作業不能在到達前開始，也不能縮短其給定時長。

對 A10，單是 GPU 工作量下界約 **185.76 天**。對整個資料集，\(\max_j(a_j+p_j)\) 約 **184.06 天**。因此，即使完全沒有等待，仍不可能要求全部作業在 90 天提交窗口內完成。[C1]

這些是理想化下界，不是可達的最優解；到達分布、節點資源形狀及調度策略可使實際完工更晚。

### 5.6 多目標而非單一任意分數

建議同時呈現：

\[
\left(\overline W,\ W_{95},\ W_{99},\ W_{\max},\ M,\ -N_{done}(T)\right).
\]

若要選定單一最終策略，可以先約定極端等待或長作業群組退化的可接受範圍，再在範圍內最小化平均等待。門檻應在開發實驗中事先決定，而非看完最終表格再放寬。

## 六、離散事件模擬器與完整基線實驗

### 6.1 本次已實作的兩個基線

**FCFS：** 每種 GPU 各有一條佇列，按 `(submit_time, job_name)` 排序。佇列最前方作業不能放下時，該池停止啟動後續作業；其他型號池仍獨立調度。這避免把不共享資源的池人為鎖成一條全域阻塞佇列。

**SJF-HOL：** 每池只對已到達的等待作業，按 `(duration, submit_time, job_name)` 排序；最短作業不能放下時，該池同樣停止。`HOL` 明確表示存在隊首阻塞。它不是 SJF-fit，不會繼續尋找下一個可放置作業，也不包含回填或公平性保護。

兩者都按 `node_name` 由小到大做 First-Fit：每個節點先放入它能承受的 worker 數，直到整個作業放完。平手排序只為可重現，不把匿名 ID 解釋成真實優先級。

### 6.2 事件順序與原子性

每個時間戳依序進行：釋放全部在此刻完成的作業、接收全部在此刻到達的作業，再反覆調度直到當前策略不再啟動作業。

```text
while 還有未到達、等待或執行中的作業:
    t = 下一個到達或完成時刻
    釋放所有在 t 完成的作業
    加入所有在 t 到達的作業
    對相應 GPU 池:
        依策略選擇隊首
        建立完整放置計畫
        若不可行，保持資源狀態不變並停止本輪
        若可行，一次提交全部配置，加入完成事件
```

放置必須遵循「先計畫、完整檢查、一次提交」。計畫失敗不能留下部分 worker，佔用狀態不能藉由吞掉例外或直接跳過作業來維持。

### 6.3 本次驗證範圍

附帶程式通過手算案例：FCFS 與 SJF 排序、gang 同步啟動、單 worker 不可跨節點拆分、CPU 零請求、小數 CPU、同時完成與到達、同節點放多個 worker，以及確定性平手排序。

另外，用固定種子建立 **30 組小型隨機案例 × 2 種策略**，與獨立的逐秒、純量參考實作比較開始時間，全部一致。對兩個完整 trace 結果，獨立按節點重播全部資源配置事件，檢查每一筆 worker 配置、型號相容、開始時間、給定時長、逐節點容量及最後資源歸零，全部通過。[C1–C2]

這些驗證提供研究原型的正確性證據，但不等於生產系統部署或真實硬體效能驗證。

### 6.4 評估窗口

固定窗口採用：

\]

GPU／CPU 分配率及窗口內完成數在 \([0,T]\) 評估。等待與 JCT 則對全部 224,112 個輸入作業統計；最後一筆到達後停止注入新作業，持續模擬直到全部完成。未在窗口內完成的作業沒有被排除。

## 七、推薦主方法：等待保護的時長感知回填

### 7.1 方法定位

本文暫稱候選方法為 **Age-Guarded Duration-Aware Backfilling，AGDB**。這是本文提出的組合設計名稱，不是聲稱文獻中已有同名演算法，也不表示其效益已經完成驗證。

核心研究問題是：**能否保留 SJF 對多數作業的響應優勢，同時降低其對長作業的極端延後？**

回填的一般思想是，讓較低優先級作業先使用暫時空閒資源，但不推遲受保護作業的預計開始時間。Slurm 官方文件亦說明瞭這一機制及其對合理時長資訊的依賴。[W2] 本題已知 duration，適合從此方向建立方法。

### 7.2 等待保護

定義作業年齡：

\[
A_j(t)=t-a_j.
\]

以事先設定的門檻 \(\theta_g\) 建立受保護集合：

\[
\mathcal P_g(t)=\{j:g_j=g,\ A_j(t)\ge\theta_g\}.
\]

當受保護集合非空，按到達順序保護最早作業；其餘可填空的作業按已知時長排序。沒有受保護作業時，可以優先短作業，但仍遵守資源與同步約束。

**\(\theta_g\) 是進入保護的觸發條件，不是等待時間的硬上限。** 正在執行的長作業不能搶佔，前方受保護作業也可能仍在等待。沒有額外可行性證明，不能寫「所有作業必在 \(\theta_g\) 內開始」。

### 7.3 可證明安全的資源預約

對受保護作業 \(h\)，根據當前執行作業的已知完成時刻，找到忽略後續新作業時最早可完整放置它的時刻 \(R_h\)。維持這份預約，不允許回填作業把它推遲。

對一個在 \(t\) 啟動的候選作業 \(j\)，

\[
t+p_j\le R_h
\]

是簡單的充分安全條件：它會在預約之前完成，因而不影響預約時刻的資源。這個條件不是必要條件；部分超過 \(R_h\) 才完成的作業，也可能因為使用了與預約無衝突的節點而可安全回填。

第一版可以採較保守的時間條件，但應明確命名為「時間界線式受保護回填」；不能把它與支援精確空間預約的完整 EASY 實作不加區分。更強版本需對逐節點的預約時段驗證資源可行性。

### 7.4 放置策略

首先保留本次已驗證的 First-Fit，作為一致的共同放置器。再加入 Best-Fit 或資源形狀感知版本，判斷它在多 GPU 節點是否確實帶來改善。

若使用「放置後剩餘 CPU 與 GPU 比例差」或「剩餘資源總量」作評分，這只是啟發式代理量，不是未來碎片化最優性的證明。候選節點的排序與精確可行性判定應分開：節點搜尋限額不能把「未找到」冒充「全池不存在可行放置」。

對單卡 A10，預期主要收益更可能來自排序與保護；對 A100 等多卡節點，才進一步檢查放置策略的邊際貢獻。這是待驗證的研究分工，而不是已確認的因果比例。

### 7.5 精簡演算法流程

```text
on arrival / completion / 必要的保護門檻觸發事件:
    更新資源與等待集合
    選擇最早的受保護作業；若無，按已知時長選擇候選
    若可立即完整放置，原子式啟動
    若不可，建立或保留不被延後的預約
    對其餘候選按時長掃描:
        只有同時符合當前資源與預約保護才啟動
    記錄等待、資源使用、預約違反與決策成本
```

若保護門檻恰好在兩個到達／完成事件之間跨過，必須說清是「下次事件才檢查」還是增加門檻事件。兩者都可以成為明確策略，但不能實作一種、論文描述另一種。

### 7.6 研究假說

AGDB 應以可否改善等待—極端延後的 Pareto 前緣作為假說；不能預設它會同時擊敗 SJF 的平均等待與 FCFS 的最大等待。若它只改善某個公平性範圍內的平均等待，這也是可解釋的結果。若移除某個模組沒有影響，應縮減方法，而不是保留沒有證據的複雜度。

## 八、手算示例：為什麼需要受保護回填

以下是教學案例，不是原始資料中的實際作業。

有兩個相同節點，各有 1 張 GPU 和 4 vCPU。三個作業如下：

| 作業 | 到達秒數 | workers | 每 worker GPU／CPU | duration |
|---|---:|---:|---|---:|
| A | 0 | 1 | 1 GPU／4 vCPU | 10 秒 |
| B | 1 | 2 | 1 GPU／4 vCPU | 5 秒 |
| C | 2 | 1 | 1 GPU／4 vCPU | 3 秒 |

FCFS 下，A 在 0 開始；B 因需要兩個節點而等到 10；C 被 B 擋住，等到 15。等待時間分別為 0、9、13 秒：

\[
\overline W_{FCFS}=(0+9+13)/3=7.333\text{ 秒}.
\]

受保護回填給 B 預約第 10 秒。C 在第 2 秒到達時，可用空閒節點運行至第 5 秒，符合 \(2+3\le10\)，不推遲 B。等待時間變成 0、9、0 秒：

\[
\overline W_{BF}=(0+9+0)/3=3\text{ 秒}.
\]

若 C 改為執行 12 秒，它會佔用節點至第 14 秒，便不能依上述條件回填。這個例子同時說明：GPU 總量、gang 同步與未來預約必須一起考慮。

附帶程式已用同一個小型資源案例驗證 FCFS/SJF-HOL 的手算開始時刻，但**尚未實作回填器**；本節回填結果是明確可手算的示例，不是隱含宣稱已有完整 EASY 測試。

## 九、第三問方案：兼容性與時長代價明確的跨型號替代

### 9.1 額外假設

定義 \(K_{jg}\in\{0,1\}\) 表示作業 \(j\) 能否在型號 \(g\) 執行，並要求原始型號總是可行。定義替代時長：

\[
p_{jg}=\kappa_{jg}p_j,\qquad \kappa_{jg}>0.
\]

\(\kappa<1\) 表示更快，\(\kappa>1\) 表示更慢。第一版可明確假設 worker 數、每 worker GPU 數與 CPU 請求不變，只改型號與時長；這是建模選擇，不是原始資料提供的關係。啟動後所有 workers 使用同一替代型號，且不再遷移。

競賽資料沒有跨型號效能或顯存需求，所以 \(K\) 和 \(\kappa\) 必須作為有理由的情景參數，不能從型號名稱直接推得。Gavel 的研究以有效吞吐量處理硬體異質性，也說明異質調度需要工作負載相關的效能資訊，不能只按 GPU 名稱排序。[W3]

### 9.2 可解釋的替代條件

若當前狀態下原池和替代池的估計等待分別為 \(\widehat W_{j,g_j}\) 與 \(\widehat W_{jg}\)，則可比較：

\[
\widehat W_{j,g_j}+p_j
\quad\text{與}\quad
\widehat W_{jg}+\kappa_{jg}p_j.
\]

忽略其他成本時，替代有利的條件為：

\[
\widehat W_{j,g_j}-\widehat W_{jg}>(\kappa_{jg}-1)p_j.
\]

等待估計只來自當前已到達佇列與已知時長，不使用未來到達。若已有精確預約，可以由相同的預約演算法產生等待估計。

例如原池預計等待 10 小時、原執行需 4 小時；替代池等待 2 小時、\(\kappa=1.5\)，則預計完成耗時由 14 小時變為 8 小時。這只是參數化示例，不是資料中的實測加速。

### 9.3 保護接收池，而非把擁堵搬過去

本次 A100 基線零等待，替代策略應同時檢查 A100 原生作業的等待、窗口完成數與極端延後。可以採「不破壞接收池既有預約」或「限制外來作業 GPU 容量佔比」的政策，再以實驗確認代價。

這些規則會限制替代收益，但比只報 A10 降幅、忽略接收池退化更完整。不能假定昂貴 GPU 未被分配的時間在任何時刻都能無代價地接走 A10 工作。

### 9.4 建議情景矩陣

可先比較無替代、25%／50%／100% 可兼容的候選比例，以及 \(\kappa\in\{0.5,1.0,1.5,2.0\}\)。這些只是建議的初始探索網格，不是已調好的參數，也不代表真實相容比例。

可兼容集合應由固定種子或穩定雜湊抽取，且不同策略使用同一集合。結果至少報 A10 與接收池的平均／P99／最大等待、全體固定窗口完成數、型號分配率和原生作業受損幅度。

### 9.5 MIG 與定價的定位

MIG 可作高階 GPU 分割的現實動機，但分割不會憑空增加物理算力；必須同時定義每個分割單元的資源、可容納作業及執行時間變化。NVIDIA 官方支援表列有 A100 等產品，A10 和 RTX 4090 不在該表中；不能把使用者的 4090 伺服器當成 A100 MIG 平台。[W4]

定價若只有內部稀缺度分數，可以稱為資源影子價格；不能直接聲稱真實客戶會依某個折扣轉移需求。若無價格彈性與支付意願資料，實際金額定價只能是清楚標示的假設情景。[P，第 2 頁]

本文建議先把跨型號替代完整做透，不同時實作 MIG、時間切片、定價行為模型與強化學習。

## 十、評價指標、反事實診斷與實驗設計

### 10.1 指標定義

\[
W_j=s_j-a_j,\qquad JCT_j=b_j-a_j=W_j+p_j.
\]

\[
U_g^G(T)=\frac{\sum_{j:g_j=g}w_jq_j\,[\min(b_j,T)-\max(s_j,0)]_+}
{T\sum_{m:g_m=g}G_m}.
\]

CPU 分配率將 \(q_j\) 換成 \(c_j\)，並以該池總 vCPU 容量為分母。全叢集分配率應以容量時間加權，不是簡單平均各型號的百分比。

\[
N_{done}(T)=\sum_j\mathbf 1(b_j\le T),\qquad M=\max_j b_j.
\]

\[
BSD_j(\tau)=\max\left\{1,\frac{W_j+p_j}{\max(p_j,\tau)}\right\}.
\]

本次附帶結果另存 \(\tau=60\) 秒的 bounded slowdown，但 \(\tau\) 是分析設定，不是官方要求。長作業即使絕對等待很久，slowdown 仍可能不大，所以絕不能只保留 slowdown 而省略最大等待與時長分層。

在固定型號、固定 duration 的基線中，平均 JCT 與平均等待只差同一個平均 duration；兩者不是兩份獨立證據。跨型號替代改變 duration 後，兩者才需要更仔細分開比較。

### 10.2 已完成與待完成的基線層級

| 方法 | 目的 | 本次狀態 |
|---|---|---|
| FCFS + First-Fit | 到達順序、無回填基準 | 完整 trace 已完成 |
| SJF-HOL + First-Fit | 已知時長排序的收益與代價 | 完整 trace 已完成 |
| SJF-fit | 區分最短作業與隊首阻塞的影響 | 待實作 |
| 正式 EASY／精確預約回填 | 強基線，排除只擊敗弱 FCFS 的問題 | 待實作 |

| AGDB + 替代 | 剩餘型號失衡的治理 | 待情景驗證 |

### 10.3 消融

固定模擬器與資料，依次移除等待保護、回填、改進放置，再與完整候選比較。每一次都必須保留其餘決策規則，不能拿「改了排序又改了放置」的結果歸因給單一模組。

若按 GPU 嚴格分池，在同池每個作業的優先分數都加上相同「該池擁堵常數」，不會改變池內排序。擁堵訊號需要影響實際可變決策，例如跨池選擇或保護門檻，才有可消融的意義。

### 10.4 不預填因果佔比

可比較 GPU-only、CPU/GPU 共同約束、不同放置器、gang 同步與不同排序，但應稱為「約束放鬆或政策替換的反事實實驗」。移除約束後，啟發式演算法可能改變整條執行路徑；各項差異依賴比較順序與策略，未必非負，也不代表唯一的因果百分比。

若要聲稱某約束造成了多少損失，應明確寫出介入內容、共同基準、其餘條件及差值定義。對一般最優目標而言放鬆約束不會使最優值變差，但這個單調性不自動適用於某個固定啟發式的實測結果。

### 10.5 負載、容量與初始狀態敏感性

到達壓力可使用：

\[
a'_j=a_0+(a_j-a_0)/\lambda.
\]

\(\lambda>1\) 壓縮到達間隔；worker 數、資源與 duration 保持不變。必須說清固定評估窗口是否也隨之變動，避免分母與完成數口徑混亂。

容量敏感性應透過增減整個合法節點實作，不產生小數物理 GPU。另應評估同時到達作業的平手排序，因為時間 0 的大批次可能放大匿名 ID 排序的影響。

### 10.6 小規模最優參照

可對少量作業與節點建立整數規劃，研究候選策略與最優解的差距。只有取得最優性證明，才把求得目標稱為 \(J^*\)。若超時僅有可行解與求解器下界，應同時報告二者，不能把超時可行解直接當成最優解。

等待目標的最優值可能為 0；此時相對百分比差距沒有意義，應改報絕對差距。小規模離線最優解若知道全部未來到達，與線上策略的比較也必須註明資訊差異。

### 10.7 統計與泛化邊界

本次兩個基線是確定性重播。重復同一輸入與規則不會產生新的獨立證據；無需為了報告置信區間而人為添加隨機性。

若後續存在隨機抽樣或局部搜索，可使用配對隨機種子。若研究時間段穩健性，應保留隊列與執行中的作業狀態，並讓不同策略從同一原始初始條件重播，不能每到一個新日就清空叢集。

當前整份 trace 已做 EDA 與基線分析，不應把其中末段追認成「從未看過的測試集」。後續可預先鎖定方法、限定開發實驗，並把不同時間段與額外負載情景用作內部穩健性驗證；若要真正獨立泛化結論，需要新的未使用資料或明確獨立生成機制。也不應把 224,112 個有隊列依賴的作業視為 IID 樣本，直接計算看似極窄的顯著性區間。

## 十一、計算資源與 7×4090 的使用方式

### 11.1 本次已證明的計算可行性

本次原型在 ChatGPT 分析容器完成兩個完整 trace，沒有使用 GPU。每個策略約十幾秒即可完成模擬、獨立容量驗證與該策略結果寫出；具體環境與運行時間保留在 JSON 中。這個數字不含最初輸入讀取／數據統計，也不是你的服務器 benchmark。

核心開銷是事件堆、等待佇列及相容節點的資源檢查。當前 NumPy 逐池檢查已足夠支持初步研究，因此應先量測再優化，不能僅憑 \(224112\times4278\) 的最壞組合數就斷定必須 CUDA 或重寫為 C++。

正式回填的未來預約、隊列候選掃描可能更昂貴，其性能仍未測量。後續可按 GPU 類型、剩餘 GPU 數與 CPU 容量建立索引，但索引截斷必須保留正確的失敗語義。

### 11.2 七張 GPU 的合理定位

當前主任務是 CPU 上的 trace 模擬；七張 4090 不需要成為前置依賴。它們可在正式模擬完成後，支持小型真實多 GPU 作業的同步啓動、資源預留與排程開銷驗證，但不應拿其吞吐量代替 A10/A100 的替代倍率。

真實實驗還會引入 CPU、內存、通信與執行時間變化，而原題假設 duration 固定。應把它單列為機理補充，不與固定時長的 trace 主結果混為同一實驗。

### 11.3 最小計算路線

先復現附帶的稽核與兩個基線，再補齊 SJF-fit 和正式回填，隨後加入一個等待保護模塊。確認改善後再增加跨型號替代。完整深度強化學習、全 trace 整數規劃、大型拓撲模型與時長預測都不在當前關鍵路徑中。
